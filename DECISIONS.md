# Decisions

One line each. Judgement calls made while building, and why.

- Phase 0: Repo root is `d:/GharShakhi` itself (already contained the spec docs), not a nested `gharsakhi/` folder — matches where the user pointed Claude Code.
- Phase 0: Pinned `tailwindcss` to `^3.4.0` explicitly in `client/package.json` — a bare install today would pull v4, but the spec fixes Tailwind v3.
- Phase 0: Proceeding on the installed Node v24 and PostgreSQL 18 rather than the spec's pinned Node 20 / Postgres 16 — user confirmed Postgres 18 is fine; Node 24 is backwards compatible with everything in the fixed stack (Express 5, pg, etc.).
- Phase 0: `server/.env` is created locally (git-ignored) from `.env.example` with a placeholder DB password for the user to fill in; only `.env.example` is committed.
- Phase 1: Split §5.2's table list across migrations by feature: `001_init.sql` has every core table plus `payment_orders` (no dedicated file was named for it), `002_indexes.sql` has all 8 indexes, `003_push.sql` has only `push_subscriptions` — matching the three filenames the spec's repo layout names.
- Phase 1: Migration idempotency is enforced via a `schema_migrations` tracking table (filename + applied_at), not idempotent SQL bodies — Postgres has no `CREATE TYPE IF NOT EXISTS`, so re-running a migration body isn't safe; skipping already-applied files is.
- Phase 1: Added `server/src/utils/money.js` (`splitPrice`) a phase early so seed.js and the Phase 3 booking service share one commission-split implementation instead of duplicating the formula.
- Phase 1: `seed.js` wraps everything in one transaction (`TRUNCATE ... RESTART IDENTITY CASCADE` then re-insert) so a failed reseed never leaves partial data; this is a one-off data loader, not a concurrent code path, so it doesn't need the `SELECT ... FOR UPDATE` locking that live money movements require.
- Phase 1: Caught during seeding — two customers' seeded bookings initially summed to more debits than their ₹2000 starting wallet, which would be impossible under the real `402 INSUFFICIENT_BALANCE` rule. Rebalanced the seeded booking price mix per customer so cumulative holds never exceed the starting balance at any point in the chronological sequence; `seed.js`'s reconciliation report now also asserts customer balances are non-negative.
- Phase 1: Added `004_balance_constraints.sql` — DB-level `CHECK (wallet_paise >= 0)` on both `customers` and `workers`, at the user's request, as defense-in-depth: the seed assertion only catches bad seed data, this makes a negative balance impossible from any code path, including a future buggy Phase 3 transaction. Verified live by attempting a direct negative `UPDATE`, which Postgres rejected.
- Phase 2: Zod schemas for register/login are defined inline in `routes/auth.js` rather than a separate `validators/` folder — the spec's repo layout doesn't name one, and there are only 4 schemas so co-locating keeps the file count down without hurting readability.
- Phase 2: §7.5's "blocked accounts can log in but every write endpoint returns 403 ACCOUNT_BLOCKED" isn't enforced anywhere yet — Phase 2 has no write routes beyond registration (account creation, where `is_blocked` is always false by definition). This will be added to the booking/profile write routes starting Phase 3.
- Phase 2: `notFoundHandler` is mounted only under the `/api` prefix so it never swallows a future non-API route; the central `errorHandler` is mounted globally last, after all routers, per Express's error-middleware convention (4-arg signature).
- Phase 3: `GET /api/services` and `GET /api/areas` live in `routes/booking.js` (mounted at `/api`) rather than a new `catalog.js` — the spec's file list doesn't name a home for them, and they're read-only prerequisites for booking creation, which is the rest of that same file.
- Phase 3: Route-level ownership/ID mismatches (a booking that doesn't exist, or exists but belongs to someone else) both return `404 NOT_FOUND`, not `403 FORBIDDEN` — avoids leaking booking-ID existence to a caller who doesn't own it. Matches the acceptance checklist's "customer cannot read another customer's booking" without adding a new error code.
- Phase 3: `decline`'s `reason` is required (non-empty string), not optional — a decline with no reason gives the customer nothing to act on; the schema in the spec's API table just says `{reason}` without marking it optional.
- Phase 3: §7.5's `ACCOUNT_BLOCKED` check is done differently per route depending on which row is already being locked for money movement: `create`/`cancel` get it for free off the `SELECT ... FOR UPDATE` on the customer row; `complete` gets it free off the `FOR UPDATE` on the worker row; `accept`/`decline` (which lock only the booking, no wallet mutation for the acting party) do one extra plain `SELECT is_blocked` on the worker — cheap and lock-free, so it can't introduce a new deadlock ordering.
- Phase 3: Lock order is enforced as *booking → customer → worker* wherever more than one is locked in the same transaction (decline: booking then customer; complete: booking then worker); `create` only ever locks the customer since no booking row exists yet to lock first.
- Phase 3: The smoke test hits the real running HTTP API (via `fetch`) to exercise the routes end-to-end, but reads wallet/booking state directly from Postgres for assertions, since there's no `GET` endpoint yet for wallet balances or transaction history (that's Phase 4) — direct reads are the only way to verify the ledger right now.
- Phase 3: Smoke test scenarios needing a worker-availability failure isolated from balance (offline worker, wrong area) or a blocked-account check register throwaway customers via the real API instead of reusing seeded ones, so the test doesn't depend on exactly how much balance a seeded customer happens to have left after earlier scenarios in the same run.
- Phase 3 (post-review cleanup): `acceptBooking`/`declineBooking` read the acting worker's `is_blocked` via a plain, unlocked `SELECT` before locking the booking. Accepted as-is: the worker row isn't otherwise locked in those two paths (no wallet mutation), so a plain read is enough to check blocked-status; the only race this admits is a worker going offline/blocked in the instant between that read and the transaction's commit, which just means one more request slips through on stale-but-recent data — no money is at risk (accept moves none; decline only refunds the customer, which is correct regardless of the worker's current status), and the worker can still be blocked immediately afterward. Every transaction's ROLLBACK is now wrapped in its own try/catch so a failed rollback can never mask the original error, and `createBooking`'s customer lock uses an explicit column list (`id, is_blocked, wallet_paise`) instead of `SELECT *` so `password_hash` never enters memory on a money-movement path.
- Phase 4: **TIMESTAMPTZ boundary for `from`/`to` date filters.** `from`/`to` are IST calendar dates (`YYYY-MM-DD`). IST is a fixed UTC+5:30 offset with no DST, so there's no ambiguity to resolve. `from` converts to the UTC instant of `00:00:00 IST` on that date (`b.created_at >= $N`) via `new Date('${from}T00:00:00+05:30')` — the `+05:30` suffix lets the JS Date parser compute the correct UTC instant directly, independent of the server process's own timezone. `to` deliberately does NOT use a `23:59:59.999` upper bound (fragile — depends on the column's actual timestamp precision, and Postgres timestamptz has microsecond resolution the JS Date/pg boundary could still miss by fractions of a millisecond). Instead it computes the start of the *next* IST calendar day and filters with a strict `<` (`b.created_at < $N`), which is exact regardless of precision and correctly includes every instant of the `to` day. `nextCalendarDay` rolls the date over using `Date.UTC(y, m-1, d+1)` (plain calendar arithmetic on the numeric parts, computed in UTC so the host machine's local timezone can never leak in) rather than string math, so month/year rollovers (e.g. `2026-01-31` → `2026-02-01`, `2026-12-31` → `2027-01-01`) are handled by `Date`'s own normalization, not manual carry logic. Verified live: booking 13 (created `2026-07-24T09:40:22Z`, i.e. `2026-07-24` IST) is included by `?from=2026-07-24&to=2026-07-24`, excluded by `?to=2026-07-23` (upper bound `2026-07-23T18:30:00Z`, before the booking), and excluded by `?from=2026-07-25` (lower bound `2026-07-24T18:30:00Z`, after the booking).
- Phase 4: `page_size` isn't in the spec's documented query-string list for any endpoint, but the instruction to "cap page_size at 50 regardless of what the client asks for" implies a client might try to send one. Accepted an optional `page_size` (default 20, clamped to `[1, 50]` in `parsePagination` — non-numeric/negative/zero all fall back to the default via `Math.trunc(Number(x)) || default`) rather than rejecting the param outright.
- Phase 4: `createReview` inserts the review first, then locks the worker row (`FOR UPDATE`) before recomputing `rating_avg`/`rating_count` from `SELECT COUNT/AVG ... WHERE worker_id=$1`. This order is still race-safe for concurrent reviews of the *same* worker: whichever transaction's recompute+commit runs last under the lock will see every previously-committed review (including ones inserted-but-blocked-on-the-lock by a concurrent transaction, since that transaction can't reach recompute until the first one commits) — the lock only needs to serialize the recompute step, not the insert.
- Phase 4: `GET /api/worker/requests` is NOT wrapped in the `{data,page,page_size,total}` envelope — the spec describes it as an unfiltered, always-pending-only list (typically a handful of rows) with no query params documented in §8, unlike the explicitly paginated history/wallet endpoints.
- Phase 4 (adversarial review pass — 4-dimension workflow, 3 findings, all confirmed, 0 false positives): fixed three bugs, landed as a separate commit from the Phase 4 build itself.
  1. **`total=0` on an empty page, even when earlier pages have data.** The original design read `total` off a `COUNT(*) OVER()` window column riding along on the paginated data query. That column only appears on rows the query actually *returns* — if `page`/`offset` lands beyond the last matching row (a normal, valid request, e.g. a stale client-side page number after the underlying data shrank), the query legitimately returns zero rows, so `rows[0]` is `undefined` and `total` silently fell back to `0` instead of the real count. Fixed by running an explicit `SELECT COUNT(*)::int AS total FROM ... WHERE <same filter clauses>` as its own query before the paginated data query, reusing the identical `WHERE` clause and params array so the two can never disagree. This is a deliberate reversal of the earlier "one query per list" window-function trick — correctness wins over the round-trip count. Affected and fixed: `listCustomerBookings`, `listWorkerBookings`, `getWorkerReviews`, `getCustomerWallet`/`getWorkerWallet`. Verified live: a worker with 2 bookings requesting `?page=3&page_size=1` now returns `{data: [], page: 3, page_size: 1, total: 2}`.
  2. **`createReview` never checked the submitting customer's `is_blocked`.** Every other write path in `bookingService.js` (create/accept/decline/complete/cancel) throws `ACCOUNT_BLOCKED`; this one, added in Phase 4, was missed. Fixed by adding the same plain `SELECT is_blocked FROM customers WHERE id=$1` check used elsewhere, before touching the booking. Verified live: blocked a customer with a completed-but-unreviewed booking, confirmed the review attempt returns `403 ACCOUNT_BLOCKED` and inserts zero rows into `reviews`.
  3. **`getWorkerProfileDetail` filtered `is_blocked = FALSE`, inconsistent with the rest of the app.** The original Phase 4 entry (now replaced by this one) reasoned this matched §7.5's matching-exclusion rule, but every *other* booking-history read path (`listCustomerBookings`, `listWorkerBookings`, `getCustomerBookingDetail`) already joins the worker unconditionally and freely shows a blocked worker's name/photo/rating — so a customer with a legitimate past completed booking could see that worker everywhere in their history except by opening the profile itself, which 404'd. Removed the filter entirely: `matchWorkers` (search) and `createBooking`'s re-verification already independently exclude blocked workers from discovery and new bookings, so this endpoint no longer needs its own copy of that rule — it's a plain profile lookup, not a discovery surface. Verified live: blocked a worker, confirmed `GET /customer/workers/:id` for them now returns `200` with their profile, while `GET /customer/workers?service_id=&area_id=` (matching) still correctly excludes them.
- Phase 5: `adminService.getStats()`'s **GMV and commission-earned are computed over `completed` bookings only**, not all bookings regardless of status. GMV is meant to represent value actually delivered through the platform; a `pending`/`accepted` booking has money in escrow but no service has been rendered yet, and a `declined`/`cancelled` booking never happened at all (the hold was fully refunded) — including either in "gross merchandise value" would overstate real platform activity. `commission_paise` follows the same filter for consistency (a booking that never completes never actually earns the platform anything, even though the snapshot column has a nonzero value sitting on the row).
- Phase 5: `pushBookingFilters` (previously a private helper in `bookingService.js`) is now exported and reused by `adminService.listBookings`, rather than duplicating the status/service_id/from/to WHERE-building logic — single source of truth for that filter set, and the admin endpoint gets `service_id` filtering "for free" even though the spec's `GET /api/admin/bookings` query list only names `status/from/to/page` (harmless: nothing exposes it unless a future route schema explicitly adds `service_id` to admin's query validation).
- Phase 5: `setWorkerBlocked` forces `is_online = FALSE` only when *blocking* (`CASE WHEN $1 THEN FALSE ELSE is_online END`) — unblocking never forces a worker back online, since going online is the worker's own action via the dashboard toggle (§9), not something an admin unblock should do on their behalf.
- Phase 5 part 2: `routes/admin.js` is the first router mounted behind `adminAuth` rather than `auth('customer'|'worker')`, so its role check was verified live end-to-end (not just by reading the middleware): a customer token and a worker token against `/api/admin/stats` both return `403 FORBIDDEN`, no token returns `401 UNAUTHORIZED`, and an admin token returns `200`. Also verified live: blocking a currently-online worker forces `is_online: false` in the same response and immediately removes them from `GET /customer/workers` matching; unblocking them afterward returns `is_online: false` still — confirms the CASE-based force-offline only fires on the blocking transition, never on unblock.
- Phase 6: No separate `RoleSelect` page. The landing page's two CTAs ("I need help at home" / "I want to work") go straight to `/login/customer` and `/login/worker` — they already *are* the role selection; an intermediate role-select screen would just be an extra click to the same decision.
- Phase 6: `Login` and `Register` are single role-parametrized components (routes `/login/:role`, `/register/:role`), not four near-duplicate files — matches the repo layout's singular "Login, Register" naming under `pages/public/`, and the customer/worker forms differ by only a few fields (worker adds service/area checkbox grids). Admin gets its own dedicated `AdminLogin.jsx` since it's a different shape entirely (username, no register) and is deliberately not linked from anywhere on the landing page.
- Phase 6: Login/Register/AdminLogin are built as real, working pages now, not placeholders, even though the phase's bullet list only named the shell/layouts/landing explicitly. `AuthContext`'s login flow needs a real entry point to be exercised at all, and per §9 these are "Public" screens with no later phase revisiting them — building them as placeholders now would mean never coming back to finish them.
- Phase 6: All three named layouts (`CustomerLayout`, `WorkerLayout`, `AdminLayout`) are thin wrappers around one shared `layouts/PanelLayout.jsx` that does the actual responsive nav (bottom tab bar <768px / horizontal top bar 768–1023px / left sidebar ≥1024px per §4.4) — only the nav item list and brand label differ per role, so the breakpoint logic has one source of truth instead of being tripled.
- Phase 6: Admin's nav has 5 items (Dashboard/Bookings/Customers/Workers/Transactions) despite §4.4's "3–4 tabs per role" guidance — §9 names 5 top-level admin screens and Admin is primarily a desktop tool, so all 5 render as bottom tabs on mobile rather than folding two together into an invented "People" grouping not in the spec.
- Phase 6: Every "soft" background in `StatusPill`/`EmptyState`/`ErrorState` uses an opacity modifier on a `gs-*` token (e.g. `bg-gs-danger/10`) instead of Tailwind's default `red-50`/`gray-100`/etc., per the "no hardcoded hex, no generic-AI-dashboard look" instruction — every color on screen traces back to the 9 palette tokens, none of Tailwind's stock palette leaks in.
- Phase 6: `Button` is polymorphic (`as` prop, defaults to `'button'`) so the landing page's CTAs and other nav-style actions can render as a real `react-router` `Link` while reusing the same variant styling — and it now defaults native buttons to `type="button"` (previously unset, which meant a `Button` used for anything other than a form's actual submit action would default to `type="submit"` and could trigger an accidental submit inside a `<form>`).
- Phase 6: `axios`'s 401 interceptor does a hard `window.location.assign(...)` redirect rather than `useNavigate()`, since interceptors run outside the React tree with no router context; both it and `AuthContext` read/write through one shared `auth/storage.js` (localStorage keys + role→path lookups) so the two can't drift on key names or redirect targets.
- Phase 6: Verified with Playwright (chromium installed on-demand via `npx playwright install`, not added to `client/package.json` — this was a one-off verification, not a project dependency) since no browser tool was available in-session. Beyond the requested landing-page + 375px checks, also drove the full login → protected-route → layout → logout cycle: confirmed a logged-in customer visiting `/worker` is bounced to their own home (`/customer`), not to a login page, and that logout returns to `/`.
- Phase 7 part 1: No new backend endpoints. The Home screen's wallet balance comes from the already-existing `GET /api/customer/wallet` (live, not the login-time snapshot); the customer's name/area/address come from the `user` object `AuthContext` already stores at login (`registerCustomer`/`loginCustomer` return the full row minus `password_hash`, including `area_id`/`address_text`) — accurate enough since there's no profile-edit screen yet to make it stale.
- Phase 7 part 1: Worker cards show "`{rating_count} jobs done`" - `matchWorkers` (§7.4) only returns `rating_avg`/`rating_count`, not a count of completed bookings, and adding one would mean touching the backend in a frontend-only phase. `rating_count` (reviews received) is a strict lower bound on jobs actually completed, not the same number - flagging this as an approximation to revisit if/when the backend exposes a real completed-jobs count.
- Phase 7 part 1: `BookingConfirm` is a standalone route (`/customer/book/confirm`, not nested under `CustomerLayout`) with its own minimal header and a `fixed` bottom action bar, rather than living inside the tab-bar/sidebar chrome like every other customer screen — §4.4 explicitly calls for "a sticky action bar for booking confirmation," and stacking a second sticky bar on top of the persistent bottom tab bar on mobile would be cluttered. `BrowseWorkers` (area + worker list) stays inside the normal layout since the spec's sticky-bar callout is specific to the confirm step.
- Phase 7 part 1: The wallet "before → after" preview on the confirm screen is a plain client-side subtraction (`balance - price`) for *display only* - this isn't the "never compute price client-side" rule being violated, since no arithmetic here determines what the server actually charges; the real debit is decided authoritatively inside `createBooking`'s transaction from its own fresh DB read, and the preview is just read-then-subtract for the user's benefit, matching the spec's "the debit is never a surprise" requirement.
- Phase 7 part 1: `WORKER_UNAVAILABLE`'s recovery action ("See who else is available") navigates back to `/customer/book/:serviceId`, which remounts `BrowseWorkers` and re-runs `matchWorkers` from scratch - that remount *is* the "refresh," rather than adding a second, separate refetch mechanism.
- Phase 7 part 1: Verified against the real app, not just via `curl` - logged in as a seeded customer through the actual UI, clicked through Home → service icon → area/worker browse → confirm → booking creation, then read the resulting `bookings` and `wallet_transactions` rows directly from Postgres. Confirmed: balance dropped from 55300 → 20400 paise (exactly `bathroom_cleaning`'s 34900 price), a single `hold` transaction was written with `amount_paise: -34900` and `balance_after_paise: 20400` matching the customer's new balance exactly, and the booking's `status` is `pending`. Repeated the full flow at 375px with a second seeded customer (Rahul) and confirmed no horizontal overflow on any of the four screens (home, browse, confirm, post-booking). Incidentally caught that Rahul's seeded pending booking surfaces correctly as the Home screen's active-booking banner - a test-script selector ambiguity (`text=` matching the banner before the service grid) rather than an app bug, fixed by targeting the grid link's exact accessible name.
