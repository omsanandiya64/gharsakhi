# Decisions

One line each. Judgement calls made while building, and why.

- Phase 0: Repo root is `d:/GharShakhi` itself (already contained the spec docs), not a nested `gharsakhi/` folder — matches where the user pointed Claude Code.
- Phase 0: Pinned `tailwindcss` to `^3.4.0` explicitly in `client/package.json` — a bare install today would pull v4, but the spec fixes Tailwind v3.
- Phase 0: Proceeding on the installed Node v24 and PostgreSQL 18 rather than the spec's pinned Node 20 / Postgres 16 — user confirmed Postgres 18 is fine; Node 24 is backwards compatible with everything in the fixed stack (Express 5, pg, etc.).
- Phase 0: `server/.env` is created locally (git-ignored) from `.env.example` with a placeholder DB password for the user to fill in; only `.env.example` is committed.
- Phase 1: Split §5.2's table list across migrations by feature: `001_init.sql` has every core table plus `payment_orders` (no dedicated file was named for it), `002_indexes.sql` has all 8 indexes, `003_push.sql` has only `push_subscriptions` — matching the three filenames the spec's repo layout names.
- Phase 1: Migration idempotency is enforced via a `schema_migrations` tracking table (filename + applied_at), not idempotent SQL bodies — Postgres has no `CREATE TYPE IF NOT EXISTS`, so re-running a migration body isn't safe; skipping already-applied files is.
- Phase 1: Added `server/src/utils/money.js` (`splitPrice`) a phase early so seed.js and the Phase 3 booking service share one commission-split implementation instead of duplicating the formula.
- Phase 1: `seed.js` wraps everything in one transaction (`TRUNCATE ... RESTART IDENTITY CASCADE` then re-insert) so a failed reseed never leaves partial data; this is a one-off data loader, not a concurrent code path, so it doesn't need the `SELECT ... FOR UPDATE` locking that live money movements require.
- Phase 1: Caught during seeding — two customers' seeded bookings initially summed to more debits than their ₹2000 starting wallet, which would be impossible under the real `402 INSUFFICIENT_BALANCE` rule. Rebalanced the seeded booking price mix per customer so cumulative holds never exceed the starting balance at any point in the chronological sequence; `seed.js`'s reconciliation report now also asserts customer balances are non-negative.
- Phase 1: Added `004_balance_constraints.sql` — DB-level `CHECK (wallet_paise >= 0)` on both `customers` and `workers`, at the user's request, as defense-in-depth: the seed assertion only catches bad seed data, this makes a negative balance impossible from any code path, including a future buggy Phase 3 transaction. Verified live by attempting a direct negative `UPDATE`, which Postgres rejected.
- Phase 2: Zod schemas for register/login are defined inline in `routes/auth.js` rather than a separate `validators/` folder — the spec's repo layout doesn't name one, and there are only 4 schemas so co-locating keeps the file count down without hurting readability.
- Phase 2: §7.5's "blocked accounts can log in but every write endpoint returns 403 ACCOUNT_BLOCKED" isn't enforced anywhere yet — Phase 2 has no write routes beyond registration (account creation, where `is_blocked` is always false by definition). This will be added to the booking/profile write routes starting Phase 3.
- Phase 2: `notFoundHandler` is mounted only under the `/api` prefix so it never swallows a future non-API route; the central `errorHandler` is mounted globally last, after all routers, per Express's error-middleware convention (4-arg signature).
- Phase 3: `GET /api/services` and `GET /api/areas` live in `routes/booking.js` (mounted at `/api`) rather than a new `catalog.js` — the spec's file list doesn't name a home for them, and they're read-only prerequisites for booking creation, which is the rest of that same file.
- Phase 3: Route-level ownership/ID mismatches (a booking that doesn't exist, or exists but belongs to someone else) both return `404 NOT_FOUND`, not `403 FORBIDDEN` — avoids leaking booking-ID existence to a caller who doesn't own it. Matches the acceptance checklist's "customer cannot read another customer's booking" without adding a new error code.
- Phase 3: `decline`'s `reason` is required (non-empty string), not optional — a decline with no reason gives the customer nothing to act on; the schema in the spec's API table just says `{reason}` without marking it optional.
- Phase 3: §7.5's `ACCOUNT_BLOCKED` check is done differently per route depending on which row is already being locked for money movement: `create`/`cancel` get it for free off the `SELECT ... FOR UPDATE` on the customer row; `complete` gets it free off the `FOR UPDATE` on the worker row; `accept`/`decline` (which lock only the booking, no wallet mutation for the acting party) do one extra plain `SELECT is_blocked` on the worker — cheap and lock-free, so it can't introduce a new deadlock ordering.
- Phase 3: Lock order is enforced as *booking → customer → worker* wherever more than one is locked in the same transaction (decline: booking then customer; complete: booking then worker); `create` only ever locks the customer since no booking row exists yet to lock first.
- Phase 3: The smoke test hits the real running HTTP API (via `fetch`) to exercise the routes end-to-end, but reads wallet/booking state directly from Postgres for assertions, since there's no `GET` endpoint yet for wallet balances or transaction history (that's Phase 4) — direct reads are the only way to verify the ledger right now.
- Phase 3: Smoke test scenarios needing a worker-availability failure isolated from balance (offline worker, wrong area) or a blocked-account check register throwaway customers via the real API instead of reusing seeded ones, so the test doesn't depend on exactly how much balance a seeded customer happens to have left after earlier scenarios in the same run.
